# Session 2026-08-22: the review stack, a coverage bug, and a negative result

Three threads. One of them is a finding that says *don't* do the obvious thing.

## 1. 209 commits, reshaped into 35 reviewable branches

Upstream has not moved since PR #2 and the creator has been unresponsive for
about a week. The working branch is 225 files and +124,881 lines ahead of it,
which no one can review in one pass — and reviewing it is the only thing between
this work and upstream.

The same content is now also published as **35 stacked branches**: six
foundation PRs that a reviewer reads once (splat configs, NID resolution,
headers, build gates, matching pipeline, the compiler write-up), then **one PR
per module**, smallest first, then the engineering log. Full description in
`docs/22-pr-stack.md`.

Two things make it trustworthy rather than merely tidy:

- `scripts/pr_stack.py` generates it. The first cut was built by a script in
  `/tmp`, which is exactly the mistake docs/21 records against the 19/28 hybrid
  figure — a headline artifact that cannot be regenerated from the repository is
  an anecdote, not a result.
- The generator **fails if any changed file matches no rule**, rather than
  quietly leaving it out. An unassigned file would mean the stack silently
  claims less than we have.

Its invariant is one command: `scripts/pr_stack.py --check` verifies the tip is
byte-identical to the working branch.

**The design constraint is the creator's own reaction to PR #4** — that it is
"just 50k lines of yml files". He was reading a 99-file diff whose bulk is
generated. That is a fair complaint about presentation, and the stack answers it
by keeping generated bulk in a branch of its own and leading each PR with its
claim.

Nothing is opened upstream yet. Dropping 35 pull requests on a dormant
repository reads as pressure, not contribution.

## 2. The sweep had been probing a third of rel_duel_eng

`auto_decomp.py` cut its work list with `todo[:args.limit]`, and each shard then
reported only `trying 325`. Multiply that out and the last full sweep of
`rel_duel_eng` covered **2,600 of its 7,487 functions**. The module read as
exhausted while 4,887 functions had never been looked at once.

Worse, the truncated run then **overwrote the census**. 851d9f3 established that
a `--only` subset must not replace a census, but `--only` is not the only way to
cover a subset: `--max-words` and `--limit` truncate just as silently. Running
`--max-words 8 --limit 5` on rel_password duly replaced a 3-match census with an
empty one. The guard now tests *coverage*, not which flag caused it.

A run now prints what it is not probing and why, and records it as `excluded`:

    rel_duel_eng: 7487 functions, trying 302 (1465 not in --only) [shard 1/20]

**A cap that is not printed is indistinguishable from coverage.** The project
already had "no silent caps" as a principle; it was not enforced in the one
place that decides how much of the game gets looked at.

### The same error, in the analysis

An ad-hoc query over the raw census claimed a 314-function "tail call" family in
rel_duel_eng, enriched 5x over base rate. Run through the baseline filter that
`near_misses.py` already had, **356 of those 410 were matched weeks ago** and
only 54 are open. Querying a census without subtracting what is already done
manufactures levers that do not exist.

`near_misses.py --families` now does this properly: it groups the queue by
structural features of the *target* and reports each family against its base
rate across the module. The base rate is the point — 46% tail calls means
nothing until you know the module is 9% tail calls to begin with.

Run project-wide, it says there is **no dominant structural family left**. The
remaining near-misses are ordinary functions whose drafts come out one to eight
words too long.

## 3. Gate 1: 80% -> 88% compiling, and zero new matches

Two changes, both measured on the pinned 200-draft sample:

**Pointer returns inferred from the draft.** `referenced()` builds declarations
from the ASM, before m2c has drafted anything, so it cannot know how a call's
result is used and declares every callee `extern int f();`. When the draft then
writes `*func_0003FBD4(arg0)`, mwcc rejects it — the largest single failure
class, 16 of 40. The draft is its own evidence: if it dereferences the result,
the callee returns a pointer.

Declared `int *`, **not** `void *`. The first attempt used `void *` and moved
the number not at all: dereferencing a void pointer is illegal too, so all it
did was relabel six failures from "pointer/array required" to "illegal
operands". A fix that does not move the number is not a fix.

**The compiler repairs its own diagnostics.** mwcc reports an implicit
conversion with the line number, the offending line, and both types, so
`compile_candidate()` casts the right-hand side to the type it names and
recompiles, bounded to six repairs. The cast is codegen-neutral — an
int/pointer conversion emits no instruction on MIPS.

Result: 160 -> 176 of 200 drafts compile, and "illegal implicit conversion"
falls 15 -> 5.

### And it produced no additional matches

Four modules re-run end to end give exactly the counts they had before:
rel_gallery 22, rel_limitlist 6, rel_cardalbum 6, rel_conv_machine 15.

**The drafts this unblocks are wrong for reasons that are not type errors.** For
these modules gate 1 is not the binding constraint; gate 2 is. This is recorded
because the opposite is the natural assumption, and acting on it means chasing
compile rate — a number that moves easily — instead of match rate, which does
not. It also settled a live decision: the in-flight sweep was *not* restarted to
pick up the change, because the evidence says it would buy nothing.

The change is kept. It is cheap, it removes a real failure class, and it costs
nothing when it does not help.

## Also

`merge_matches.py` now names its rejects and says what happened to each — either
"did not compile in context" or which neighbours it broke. Every candidate
reaching the merge has already verified byte-identical *alone*, so a rejection
means the surrounding file changed its codegen. That is a lever, and a bare
"added N of M" hid it completely.
