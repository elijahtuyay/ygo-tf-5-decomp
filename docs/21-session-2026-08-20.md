# Session 2026-08-20: the hybrid gate, and the fingerprint falsified

Two threads, both aimed at the "hard limits" list rather than at the match count.

## Results

| | before | after |
|---|---:|---:|
| modules building byte-exactly (`HYBRID=1`) | 19 (unreproducible) | **28 / 28 (reproducible)** |
| the `.comment` compiler thesis | open, "decisive experiment unrun" | **falsified** |

No functions were matched. Both changes are to infrastructure and to what we
believe.

## 1. The hybrid gate: 28 of 28, and it reproduces now

`HYBRID=1` is the only path that can ever COMPLETE the 19 modules containing
hand-written assembly, because plain `SRC=1` replaces the whole `.text` and so
demands that every function match — impossible when 248 of them are asm by
construction. Three things were wrong with it.

**The timeout lived in a throwaway script.** docs/19 records the 19/28 figure as
coming from `/tmp/hyb2.sh`, which no longer exists. The headline reliability
result could not be reproduced from the repo. It is now `scripts/hybrid_sweep.sh`
plus a `MWCCGAP_TIMEOUT` in the Makefile.

**The hang was not wibo, and it is now fixed rather than contained.** docs/19
attributes it to "a subprocess pipe deadlock under wibo", and only ever under
concurrency. Both claims are wrong.

It is not mwccgap's pipe handling: its two subprocess sites use
`Popen(...).communicate()`, which drains stdout and stderr concurrently and
closes stdin, and Python 3 passes `close_fds=True`. And it is not wibo — a hung
process has **no children at all**. Catching one in the act shows where it
really sits:

    $ ps -o pid,etime,pcpu,wchan -p <pid>
      82475  05:43  0.0  unix_stream_read_gen
    $ ls -l /proc/82475/fd
      0 -> socket:[357500]

Blocked reading **fd 0**. The cause is the third and fourth line of
`tools/mwccgap/mwccgap.py`:

    read_from_file = sys.stdin.isatty()
    if not read_from_file:
        in_lines = sys.stdin.readlines()

Whenever stdin is not a terminal, mwccgap reads stdin to EOF. Run it by hand and
stdin is a tty, so it returns immediately and everything works. Run it from a
script, a cron job, or any harness that hands it an open socket, and it blocks
forever on a read that will never return. That is the entire "one to four hours
at 0.0% CPU", and it looked concurrency-related only because the runs without a
controlling terminal were the background ones.

The fix is `< /dev/null` on the invocation. `timeout` and `flock` are kept as
insurance — a bound turns any future stall into a clear failure instead of a
silent CPU squat, and serialising prevents two builds racing the same output —
but they are no longer load-bearing. No module has timed out since.

**`INCLUDE_ASM` re-declared the function it was splicing in.** The macro in
`include/hybrid_asm.h` expanded to `extern int NAME()`, which collides with any
forward declaration `src/<module>.c` already carries:

    identifier 'func_00000294()' redeclared
    was declared as: 'void ()'   now declared as: 'int (...)'

That alone was failing rel_movie_viewer, rel_duel_mgr and rel_debug_menu. The
macro now declares an unrelated dummy object (`extern int __include_asm_##NAME`)
instead. **Deleting the offending prototype would have been the wrong repair** —
a prototype with real argument types governs argument promotion at every call
site, so dropping it can silently change the codegen of functions that currently
match.

**`rel_debug_menu` is fixed.** docs/19 called it the one module that "genuinely
fails and needs diagnosis". It was this macro collision, nothing module-specific.

Notable: **rel_movie_viewer and rel_html_view now both build byte-exactly**,
carrying their one stubborn function as assembly. The two modules that have been
described as blocked for weeks are, by the only definition of done that can
apply to them, complete.

**Three more bugs behind the same gate**, all found by classifying the failures
rather than guessing:

1. **Inter-function declarations were attributed to the wrong function.** A
   block ran `[definition, NEXT definition)`, which attaches the text between
   two functions to the one ABOVE it. The merge tooling emits each function's
   prelude — its `MATCH` header comment and the `extern` declarations it needs —
   immediately BEFORE the definition, so that text belongs to the function
   BELOW. Getting it backwards deleted a kept function's declarations whenever
   the function above it happened to be carried as assembly.

   Hoisting all the gaps into the preamble instead was tried first and is
   **wrong**: these preludes deliberately declare the same global at different
   types for different functions (`src/rel_story.c` declares `D_00034488` as
   both `char` and `s32`), so collecting them collides them at file scope. It
   cost rel_story its byte-exact build until the attribution was fixed properly.

2. **File-scope externs collide once functions are reordered.** Output is in
   ADDRESS order while `src/<module>.c` is in neither address nor any other
   stable order — they disagree for 8 of 9 modules sampled. Reordering can float
   a file-scope `extern int D_00027918` above a block-scope
   `extern void *D_00027918`, and then it poisons every later block-scope
   declaration. docs/20 section 4 already gives the rule (declare externs at
   BLOCK scope, always); `make_hybrid.py` now demotes exactly the offenders —
   a file-scope extern whose symbol is declared at a different type elsewhere in
   the file — and leaves uncontested ones alone, so modules that already build
   cannot be disturbed. That fixed rel_charalist.

3. **Cross-function `.L` references dangled.** Splitting `.text` into one `.s`
   per function leaves any reference crossing a boundary undefined, since gas
   keeps `.L` names out of the symbol table. In rel_cutin_viewer these are not
   branches but absolute address references — `lui %hi(.L00010B48)` /
   `sw %lo(.L00010B48)($v0)` — reaching into another function. Every such name
   encodes its own vram, so the Makefile now PROVIDEs them exactly as it already
   does for `D_XXXXXXXX` and `jtbl_XXXXXXXX`.

   Two alternatives were tried and rejected, both instructive. `.globl` on the
   label breaks mwccgap: it sizes its nop placeholder by counting lines it does
   not recognise as directives, has no case for `.globl`, and so trips its own
   "Not enough assembly to fill" assertion — and patching mwccgap is no good
   because `tools/` is gitignored, so the fix would neither be committed nor
   reproduce for anyone else. Merging the two functions into one `.s` assumes
   splat split one real function; a guard checking adjacency showed the
   functions involved are not adjacent, so that assumption is false here.

**The sweep script now refuses to run twice at once.** Two concurrent sweeps
share every log and object, and the Makefile's flock makes that merely slow
rather than obviously wrong — which is exactly how you end up reading a summary
assembled from two different runs. It takes its own lock and exits.

### Two more bugs, both from mis-reading the source

4. **The function-definition pattern missed function-pointer returns.** It
   required the return type to be identifiers and stars, so
   `s32 (*func_00001EC8(void))() {` did not match — the parenthesis before the
   name defeated it. A missed definition is worse than it sounds: the function
   is absent from the kept set, so it is carried as `INCLUDE_ASM`, while its C
   body still gets emitted inside a neighbouring block. The object then defines
   it twice and the link fails with `multiple definition of func_00001EC8`.
   Recognising any column-zero line that names a function and does not end in a
   semicolon fixes it, and unblocked rel_cutin_viewer.

5. **...but "does not end in a semicolon" has to ignore comments.** The looser
   rule immediately broke rel_shop, because a forward declaration there carries
   a trailing note:

       void func_0000F928(void); /* forward decl: defined below, called ... */

   As written that line does not end in a semicolon, so it was taken for a
   definition. Comments are stripped before the test now.

### The last four, and what they were

| module | cause |
|---|---|
| `rel_duel_draw` | K&R definition `int func_0006DE84(arg0) s32 arg0;` read as a declaration, so the function was emitted twice |
| `rel_duel_eng` | bodies written on one line (`...; }`) defeated the `}`-line block scan; plus a genuine arity disagreement in the source |
| `rel_field`, `rel_tutorial` | `alabel` alternate entry points — mwccgap defines them at function-relative offsets |
| `rel_title` | `#pragma optimization_level` is file-order state and address order detaches it |

Three of these share a shape worth naming: **the generated file is not the
source file**. Anything in `src/<module>.c` whose meaning depends on its
POSITION — a pragma, a file-scope declaration, an implicit declaration that
works only because the definition comes later — changes meaning when functions
are re-emitted in address order. Every one of those had to be resolved at the
function's original position and restated explicitly in the output.

The `alabel` pair is different in kind: two independent mwccgap defects
(function-relative symbol addresses, and an unguarded `rodata_section_indices[0]`
when any local symbol is inserted) that cannot be patched here because `tools/`
is gitignored. Sidestepped by emitting those references as the literal
instruction words the disassembly already records.

### Recommendation

Make **`HYBRID=1` the definition of done for a module**, not `SRC=1`. The
Makefile header still states the latter, which is unreachable by construction
for the 19 modules containing hand-written assembly and makes the project look
further from completion than it is.

What 28/28 does and does not mean. It means every module's `.text` is
reconstructed byte-for-byte from our C plus the shipped assembly, and that the
layout, symbols and relocations are all correct — a real gate, and the one every
matching decompilation uses. It does not mean the modules are decompiled: only
2.7% of `.text` comes from C. The remaining work is unchanged, and it is the
gate-1 queue — though see the correction on docs/20: measured fresh, 84% of
drafts now compile, so gate 1 is no longer the bottleneck it was recorded as.

## 2. The `.comment` fingerprint is a LINKER stamp

Full write-up in docs/17, reproducer in `scripts/comment_fingerprint_test.sh`.

The short version: the Metrowerks linker writes `.comment` itself and ignores
what its input objects carry. Two objects both compiled by 2.3.1.01 link into a
binary claiming 2.4.1.01, under either linker version, in either order. GNU ld
merges both strings — which is why the original experiment, run with GNU ld,
concluded the opposite.

So the shipped modules' `MW MIPS C Compiler (2.4.1.01)` identifies **mwldpsp**,
and carries no information about which compiler built the code. The argument
that "the compiler is not publicly catalogued" rested entirely on it and is
unsupported. `mwccpsp_3.0.1_219` is excluded by nothing.

This agrees with the sotn-decomp counter-evidence instead of sitting in tension
with it: **the size ceiling is a methodology problem.** The 36 PS2 compilers in
`tools/` were fetched to chase this and can be dropped.

Do not screen candidate compilers with `readelf -p .comment` on a linked binary;
it is only diagnostic on an unlinked `.o`.
